# Импульс API

Бэкенд магазина «Импульс»: NestJS 12, PostgreSQL 17 (Prisma 7), TypeScript strict.

## Быстрый старт

Нужны Node.js 24+ и Docker.

```bash
cd server
cp .env.example .env        # сгенерируйте JWT_ACCESS_SECRET (команда в файле)
npm install                 # заодно генерирует Prisma Client
npm run db:up               # Postgres :5440 и Mailpit :8025 в Docker
npm run db:deploy           # миграции
npm run db:seed             # каталог, отзывы, первый администратор
npm run start:dev           # API: http://localhost:3000/api/v1
```

Затем в корне проекта `npm run dev`: Vite проксирует `/api` на `:3000`.

- Swagger UI: http://localhost:3000/api/docs (OpenAPI JSON: `/api/docs/openapi.json`).
- Вся почта в разработке попадает в Mailpit: http://localhost:8025.
- Администратор из сида: `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` из `.env`.

## Архитектура

```
src/
├── main.ts, setup-app.ts   # точка входа; HTTP-настройки, общие с e2e-тестами
├── config/                 # валидация окружения при старте (class-validator)
├── prisma/                 # PrismaService (драйвер-адаптер pg)
├── common/                 # ошибки (RFC 9457), guard авторизации, валидация, утилиты
└── modules/
    ├── catalog/            # витрина: каталог, поиск, фасеты (domain/ — чистая логика)
    ├── orders/             # оформление, жизненный цикл заказа, оплата (payments/)
    ├── auth/  account/     # аккаунты, сессии, личный кабинет
    ├── reviews/ returns/ subscriptions/
    ├── admin/              # админ-API: каталог, заказы, модерация, пользователи
    ├── notifications/      # transactional outbox и письма
    ├── audit/  health/
```

Модуль — это контроллер (HTTP и DTO), сервис (бизнес-логика и транзакции) и `domain/` (чистые функции без Nest и БД, покрыты юнит-тестами).

## API

Базовый путь `/api/v1`; health-пробы без версии: `/api/health`, `/api/health/ready`.

| Группа       | Эндпоинты                                                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Каталог      | `GET /products` (`q`, `category`, `maxPrice`, `inStock`, `sort`), `/products/search`, `/facets`, `/featured`, `/deals`, `/lookup?ids=` или `?slugs=`, `/products/:slug`, `/:slug/similar`, `GET /categories` |
| Отзывы       | `GET /reviews?category=`, `POST /reviews` 🔒, `POST /reviews/:id/helpful` 🔒                                                                                                                                 |
| Заказы       | `POST /orders` (заголовок `Idempotency-Key`), `POST /orders/track`, `GET /orders/:number` (`X-Order-Key`), `POST /orders/:number/payment`                                                                    |
| Оплата       | `POST /payments/webhooks/yookassa`                                                                                                                                                                           |
| Возвраты     | `POST /returns`                                                                                                                                                                                              |
| Подписки     | `POST /newsletter`, `GET /newsletter/confirm`, `GET /newsletter/unsubscribe`, `POST /restock-subscriptions`                                                                                                  |
| Авторизация  | `POST /auth/register`, `/login`, `/refresh`, `/logout`                                                                                                                                                       |
| Кабинет 🔒   | `GET/PATCH /me`, `POST /me/password`, `GET /me/orders[/:number]`, `/me/wishlist[...]`, `GET/PUT /me/cart`                                                                                                    |
| Админка 🔒👔 | `/admin/stats`, `POST /admin/media` (загрузка фото), `/admin/products[...]`, `/admin/categories`, `/admin/orders[...]`, `/admin/reviews`, `/admin/returns`                                                   |
| Админка 🔒👑 | `/admin/users`, `/admin/users/:id/role`, `/admin/audit-log`                                                                                                                                                  |

🔒 — нужен `Authorization: Bearer <accessToken>`; 👔 — роль MANAGER или ADMIN; 👑 — только ADMIN. Подробные схемы есть в Swagger.

## Принятые решения

**Ошибки.** Любая ошибка отдаётся как RFC 9457 `application/problem+json` с машинным полем `code` (`OUT_OF_STOCK`, `PRICE_CHANGED`, `VALIDATION_FAILED`…), человеческим `detail` и `requestId` для поиска в логах. У ошибок валидации есть `errors: [{ field, message }]`. Неизвестные поля в запросе отклоняются, а не игнорируются молча.

**Деньги.** Хранятся целыми рублями, считает их только сервер. Цена и итог от клиента лишь сверяются: при расхождении приходит `409 PRICE_CHANGED` со свежими ценами, и с покупателя никогда не спишут не ту сумму.

**Оформление заказа.**

- Идемпотентно по `Idempotency-Key`: повтор запроса (потерянный ответ, двойной клик) возвращает тот же заказ.
- Остаток резервируется атомарным условным `UPDATE … WHERE stock >= qty` в одной транзакции с созданием заказа. Строки товаров блокируются в фиксированном порядке, чтобы не было дедлоков. Последнюю единицу товара нельзя продать дважды, это проверяет e2e-тест.
- Номера заказов случайные (`IM-123456`): по ним нельзя оценить объём продаж или перебрать чужие заказы.

**Жизненный цикл заказа.** Статусы меняются только через `OrderLifecycleService`. Каждый переход проверяется статусной машиной, пишется в историю и выполняется под блокировкой строки. Побочные эффекты (возврат остатка при отмене, письмо, запись аудита) коммитятся в той же транзакции.

**Оплата.**

- За интерфейсом `PaymentGateway` две реализации: ЮKassa (боевая) и mock — тестовая страница оплаты прямо в API, в продакшене запрещена.
- Источник истины — провайдер. Вебхук, возврат со страницы оплаты и фоновая задача сходятся в `sync()`: он перечитывает платёж через API провайдера и применяет его идемпотентно.
- Вебхуки ЮKassa не подписаны, поэтому дополнительно проверяется IP отправителя.
- Неоплаченный заказ держит резерв `PAYMENT_TIMEOUT_MINUTES`, потом отменяется, и товар возвращается на склад. Платёж, пришедший после отмены, возвращается автоматически.
- Чек по 54-ФЗ включается флагом `YOOKASSA_SEND_RECEIPT`.

**Гость и заказ.** Гостю после оформления выдаётся `accessKey`: это HMAC от id заказа, его не нужно хранить. С заголовком `X-Order-Key` он открывает заказ, например после возврата со страницы оплаты. Трекинг и возврат требуют номер заказа и телефон. Ответ «не найдено» одинаков для несуществующего номера и неверного телефона.

**Авторизация.**

- Пароли хэшируются argon2id. При неизвестной почте время ответа такое же, как при неверном пароле, поэтому перебором нельзя узнать, кто зарегистрирован.
- Access-токен — JWT на 15 минут. Refresh-токен — случайная строка в httpOnly-cookie (`SameSite=Strict`, путь `/api/v1/auth`); в БД хранится только её SHA-256.
- Refresh ротируется при каждом использовании. Повторное предъявление старого токена отзывает всю цепочку сессий, это признак кражи. Исключение — первые 30 секунд после ротации: так обновляются параллельные вкладки, это не кража.
- `POST /auth/refresh` без cookie отвечает 204: это гость, а не ошибка, поэтому витрина спрашивает при каждом запуске, не засоряя консоль.
- Админ-маршруты сверяют роль с БД на каждом запросе, поэтому разжалованный менеджер теряет доступ сразу.

**Письма.** Используется transactional outbox: письмо пишется в таблицу в той же транзакции, что и событие. Воркер забирает пачки через `FOR UPDATE SKIP LOCKED` и отправляет с повторами и экспоненциальной паузой. Письмо не теряется при сбое почты и не уходит при откате транзакции. Схема безопасна на нескольких инстансах.

**Каталог и поиск.**

- Активный каталог держится в памяти и ищется тем же алгоритмом, что и на фронте: опечатки, раскладка, транслит, фразы вида «до 20 000», «в наличии», цвета. Перенесённые тесты поиска проходят на данных сервера.
- Правки в админке сбрасывают снимок, другие инстансы подхватят изменения в течение минуты.
- Примерно после 10 тысяч товаров поиск стоит вынести в Postgres (pg_trgm) или поисковый движок за тем же API.

**Безопасность HTTP.**

- Подключены helmet, CORS только для `FRONTEND_URL`, лимит тела 100 КБ.
- Rate limiting: глобально 120 запросов в минуту, на вход, оформление, трекинг и возвраты строже. За прокси нужно выставить `TRUST_PROXY`.
- Логи структурированные (pino) с `X-Request-Id`; токены, cookie и пароли маскируются.

**Фото товаров из админки.** `POST /admin/media` принимает JPEG/PNG/WebP/AVIF до 15 МБ. Тип определяется декодированием, а не заголовком, есть лимит на размер в пикселях. Фото перекодируется так же, как в медиа-конвейере витрины: AVIF и WebP шириной 160–1600, размытое превью 16 px, средний цвет, тон. Оригинал не хранится. Файлы лежат в `UPLOADS_DIR` (в Docker это том `uploads`), API раздаёт их по `/api/uploads/…` с вечным кэшем. Загрузки, не попавшие ни в один товар, удаляются раз в сутки.

**Аудит.** Каждое действие сотрудника в админке пишется в `AuditLog` в той же транзакции.

## Тесты

- `npm test`: 80 юнит-тестов доменной логики. Это поиск и фасеты, статусная машина, цены и доставка (с часовым поясом магазина), разбор номеров, IP-allowlist, валидация окружения.
- `npm run test:e2e`: 26 сценариев против настоящего Postgres. Среди них оформление, идемпотентность, гонка за последний товар, оплата через mock, истечение резерва, трекинг, статусная машина в админке, ротация и кража refresh-токена, права ролей, уведомление о поступлении. Перед прогоном тестовая база мигрируется, очищается и заполняется сидом.

## Продакшен

```bash
docker compose --profile app up --build   # Postgres + Mailpit + API в контейнере
```

- Образ многоступенчатый, запускается от непривилегированного пользователя через tini, с `HEALTHCHECK`. Перед стартом выполняет `prisma migrate deploy`.
- Обязательно задайте: `NODE_ENV=production`, длинный случайный `JWT_ACCESS_SECRET`, `PAYMENT_PROVIDER=yookassa` с ключами, реальный SMTP, `FRONTEND_URL`, `PUBLIC_API_URL`, `TRUST_PROXY`, `SWAGGER_ENABLED=false`.
- Фронтенд и API лучше держать на одном домене (`/api` через reverse proxy): так refresh-cookie остаётся `SameSite=Strict`.
- В личном кабинете ЮKassa укажите вебхук `https://<домен>/api/v1/payments/webhooks/yookassa` на события `payment.succeeded` и `payment.canceled`.
